# Замеры скорости EAGLE-3: как устроен код

Один запуск на одной H200 закрывает задачи 3a, 3b, 4 и 5 для LLaMA-3.1-8B-Instruct и официального драфта EAGLE-3. Папки `inference_speed` (этот код) и `nemo_speed` (код обучения) должны лежать рядом.

```bash
NIGHT_SECONDS=26400 nohup setsid bash night.sh > night.out 2>&1 &   # всё, с дедлайном 7 ч 20 мин
bash check.sh                                                        # то же на 2 вопросах / 40 примерах (~1 ч)
```

Ход работы печатается в `night.out` (по строке на каждую стадию: `RUNNING` / `SUCCEEDED` / `REUSED` / `FAILED`). Статус всех стадий хранится в `results/main/stages.json`, вывод каждой — в `logs/main/<стадия>.log`.

## Что делает ночь, по порядку

| # | Задача | Что | Итог |
|---|---|---|---|
| 1 | 3a | Скрипты оценки авторов без изменений: EAGLE-3 и обычная генерация, 5 бенчмарков × 80 вопросов, T=0 и T=1. Дерево статьи EAGLE-3: 60 токенов, `--depth 7` (= глубина 8), top-k 10 | `results/main/summary.md` |
| 2 | 4 | Скорость шага обучения на одних и тех же 1000 примерах: тренер авторов (DeepSpeed) в двух режимах — «как есть» и «уравненный» — против NeMo AutoModel | `../nemo_speed/artifacts/main/summary.txt` |
| 3 | 5 | Проба регенерации: как быстро таргет переписывает диалоги ShareGPT и UltraChat. Затем бюджет GPU-часов | `results/main/budget.md` |
| 4 | 3b | SGLang, тот же драфт и те же вопросы: обычный сервер и деревья 8/10/60 (как в статье), 3/1/4 (NeMo по умолчанию), 5/8/32 (документация SGLang), 6/10/60 (EAGLE-2). При T=1 — три seed | `results/main/summary.md` |
| 5 | 4 | Ускорения NeMo: packing, flash-attn 2, torch.compile, FP8, micro-batch 4 | `../nemo_speed/artifacts/main/summary.txt` |

Правила:
- **Перезапуск** пропускает готовое: у каждого результата есть отметка `<файл>.done.json` с настройками, при которых он получен. Результаты 3a, посчитанные предыдущей версией кода, принимаются (`ADOPTED`), если совпадают дерево, температура, модели, железо и пакеты окружения, а файл не менялся.
- **Упавшая стадия** получает FAILED, остальные идут дальше. Ночь останавливают только дедлайн и сигнал.
- **Окружения и модели** ставятся при первом запуске сами, по закреплённым версиям (`common.py`).

## Как считаются числа

- **3a.** Ускорение — по формуле `evaluation/speed.py` авторов (с токенизатором нашей модели): средняя по вопросам скорость EAGLE, делённая на среднюю скорость обычной генерации. Токены EAGLE берутся из счётчика генератора, токены обычной генерации — повторной токенизацией ответа; эта асимметрия у авторов, мы её сохраняем. τ `speed.py` не считает: берём определение статьи («токенов за цикл») по счётчикам генератора — `Σ new_tokens / Σ (idx + 1)`. Лимит ответа — фактические 512 токенов: `--max-new-token 1024` в скрипте авторов в генерацию не передаётся, а лимит проверяется после раунда, поэтому EAGLE может выйти за него на длину одного раунда.
- **3b.** Ускорение — отношение средних скоростей сервера с EAGLE-3 и обычного сервера (тот же seed запроса, сервер с `--random-seed 0`). Время — полный HTTP-запрос, поэтому сравнивать с 3a ускорения, а не токены/с. Кэш префиксов выключен, не больше 512 новых токенов за ход, стоп-токены как у авторов, прогрев — первый вопрос всеми ходами трижды. τ = (сгенерированные − 1) / раунды проверки: первый токен SGLang выдаёт на prefill, дальше каждый раунд даёт принятые + 1 — ровно как раунд у авторов. Счётчик SGLang «принятые + 1» оставлен для диагностики: он может включать хвост, обрезанный стоп-токеном.
- **4.** Данные и словарь на 32K общие, TTT = 7, секундомер по шагам оптимизатора после 20 шагов прогрева.
  - *Уравненный режим* (`original`, все `nemo_*`): BF16, строки по 2048 токенов, lr 5e-5 без расписания, без gradient checkpointing — одинаковая работа, сравнение реализаций.
  - *Как есть* (`original_asis`): тренер авторов со своими настройками — fp16, checkpointing, без паддинга, их расписание lr. С ним честно сравнивать NeMo с packing; именно эти строки годятся для бюджета.
  - В опубликованном `traineagle3/cnets.py` ошибка: `self.train_config.gradient_checkpointing` при словаре в `train_config` — тренер падает при создании модели. Исправляем в копии (`patch_original.py`).
  - Обучение двух стеков не одинаково и после выравнивания: сдвиг маски и нормировка loss, RoPE драфта (у авторов база 10000, у NeMo — из конфига таргета), fp32-копия весов у DeepSpeed против bf16 у NeMo, fused loss у NeMo, разные версии torch. Это сравнение **скорости двух стеков**, а не одинакового обучения.
- **5.** Пилот. Каждый сплит — отдельная страта со своим реальным размером (UltraChat `train_sft` 207 865 и `train_gen` 256 032; ShareGPT — 68K статьи, хотя скан идёт по другой версии ShareGPT). Доли групп по длине — из скана первых 8192 диалогов каждого сплита. Политика регенерации наша — в статье её нет: все ходы, greedy, ≤ 512 на ход, ≤ 1900 на пример, не влезающий диалог отбрасывается целиком (как авторский тренер отбрасывает длинные примеры). Диапазон чувствительности ×0,75–×1,5 и резерв 10 ч.

## Особенности сервера (без CUDA toolkit)

- **DeepSpeed** спрашивает `nvcc -V` при установке и при каждом импорте. Ему даётся заглушка, которая печатает версию CUDA из torch. Ничего не компилируется, оптимизатор — AdamW из torch.
- **SGLang** работает с Triton-attention и PyTorch-sampling. Пакет `kernels` удаляется: он ломает запуск сервера. SGLang 0.5.9 на старте компилирует часть ядер (RoPE) через `nvcc`, поэтому получает настоящий CUDA 12.8 из `setup_cuda.sh` (`../cuda-home`, только процессам SGLang).
- **flash-attn 2** не ставится. Варианты с ним получают статус `UNSUPPORTED`.
- **Скрипты с потоковым `datasets`** завершаются через `os._exit(0)`, потому что иначе Python падает на выходе.

История найденных проблем — в [FIXES.md](FIXES.md).
